# Phase 2 — Full Improvement Roadmap Research

**Researched:** 2026-10-31  
**Scope:** Research for the complete judge-improvement roadmap, with implementation guidance separated into immediate Phase 2 versus later phases. No application code was changed, no tests were run, and `.env` was not opened.

## Summary

Phase 2 should be a narrow conversational correctness slice: explicit crop-name resolution, clarification for ambiguous/unknown crops and unclear replies, and small explicit multi-turn state. Preserve the deterministic evaluator as the sole scheme eligibility authority. The repo’s Phase 2 roadmap already names its NLU, conversation-state, and CLI deliverables [VERIFIED: `.gsd/ROADMAP.md:31-37`; verbatim: “`backend/nlu_extractor.py`”, “`backend/conversation_state.py`”, “`cli_chat_prototype.py`”]. Its AI contract states, verbatim, “the LLM *perceives and phrases*. It never decides eligibility.” [VERIFIED: `.gsd/phases/02-text-to-text-nlu-prototype/02-AI-SPEC.md:11`].

The complete improvement plan is a multi-stage program, not one Phase 2 implementation. It labels the sequence verbatim “Stage 1 — Dialogue correctness (crop path only),” “Stage 2 — Curated knowledge base and citations,” “Stage 3 — Authenticated, private history,” “Stage 4 — Voice notice, consent, and provider review,” “Stage 5 — Production deployment,” and “Stage 6 — Offline and capacity evidence” [VERIFIED: `krishi_mitra_complete_improvement_plan.md:265-315`]. The later stages depend on the dialogue foundation and/or human provider, legal, infrastructure, and hardware decisions [VERIFIED: `krishi_mitra_complete_improvement_plan.md:275-315`]. Do not treat this research as proof of legal compliance, vendor retention behavior, offline quality, or a 1,000-user capacity claim.

**Primary recommendation:** Keep the existing Python local-web path and provider responsibilities intact; add bounded, typed dialogue behavior first, make later stages additive, and gate persistence, voice notice claims, deployment scale, and offline claims on their own tests and external review [VERIFIED: `.gsd/ROADMAP.md:31-37`; `krishi_mitra_complete_improvement_plan.md:251-315`].

### 1. Crop ambiguity and dialogue state — immediate Phase 2

- Model crop resolution as explicit states such as known alias, confirmed normalization, ambiguous candidate, and unknown/unrecognized. Preserve the user’s words and evidence; never silently map an unknown string to the closest crop. Ask one short clarification when the candidate is ambiguous or unsupported. This matches the improvement plan’s crop-path requirement [VERIFIED: `krishi_mitra_complete_improvement_plan.md:46-64`].
- Keep dialogue state small and application-owned: pending clarification/slot, confirmed facts, current intent/topic, and the last unresolved user request. A reply is either a valid answer to that pending question, a new topic, or unclear; an unclear reply should leave the pending question intact rather than overwrite known facts. Store per-turn evidence/provenance for extracted fields where practical. These are engineering recommendations, not claims that an LLM can infer confidence reliably [CITED: https://ai.google.dev/gemini-api/docs/structured-output; https://www.nist.gov/itl/ai-risk-management-framework].
- Use schema-constrained extraction only as a syntax/type boundary, then validate semantics in Python against the actual utterance and alias data. Google documents JSON-Schema structured outputs and Python Pydantic support, while explicitly presenting it as predictable structured output—not proof that extracted values are true [CITED: https://ai.google.dev/gemini-api/docs/structured-output]. Compute land-unit normalization in deterministic code and require user confirmation for ambiguous units/crop matches.
- Add regression examples for the reported “gomugomu” and “munja” cases, plus Kannada script, transliteration, code-mix, spelling variants, multiple crops, corrections, topic changes, and contradictory answers. A Kannada-speaking agricultural reviewer should adjudicate the expected canonical crop and follow-up; model-only grading is not sufficient [VERIFIED: `krishi_mitra_complete_improvement_plan.md:48-64,80-102`; CITED: https://www.nist.gov/itl/ai-risk-management-framework].

### 2. Corpus-first RAG, citations, and evaluation — later stage

- Begin with a small, reviewed, versioned corpus; store source ID, publisher, title, URL, section/page, jurisdiction, applicable crop/season/location, publication or effective date, and review date on each passage. Retrieve only relevant records, return their IDs with generated claims, and validate every displayed citation against the retrieved set. Abstain when evidence is missing, stale, or out of scope. Never allow general advice retrieval to decide scheme eligibility [VERIFIED: `krishi_mitra_complete_improvement_plan.md:66-79`; the deterministic eligibility boundary is also quoted above from the AI-SPEC].
- For a small first corpus, prefer SQLite FTS5 lexical retrieval over a vector database or a new orchestration framework. FTS5 is SQLite’s full-text search module and can rank matching rows; confirm FTS5 availability in the deployed SQLite build before relying on it, then use a simple bounded fallback for a tiny corpus if unavailable [CITED: https://www.sqlite.org/fts5.html]. Add embeddings/vector retrieval only if a labeled evaluation demonstrates inadequate recall for Kannada variants or semantic queries.
- Evaluate retrieval and answer behavior separately: retrieval recall/hit rate on a reviewed query set; citation-to-source identity; claim-level support by a qualified reviewer; freshness/scope failures; unsupported-question abstention; and Kannada/codemixed behavior. Agree acceptance thresholds after measuring a baseline, not by guessing a universal score. Google’s web-grounding documentation shows that citation annotations can be returned, but web search grounding is not a substitute for a curated, versioned local corpus [CITED: https://ai.google.dev/gemini-api/docs/google-search; NIST AI RMF].

### 3. Identity, authorization, history isolation — later, before persistence

- Keep server-side personal history disabled until a real identity provider and ownership checks are configured. Select a maintained OIDC/identity provider rather than implementing passwords, OTP, session signing, or JWT validation yourself. Derive the principal on the server from a verified session/token; never trust request-supplied user or record ownership IDs [VERIFIED: `krishi_mitra_complete_improvement_plan.md:106-119`; CITED: https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html; https://datatracker.ietf.org/doc/html/rfc9700].
- For every read/list/write/update/export/delete and voice/history operation, scope the database operation to the authenticated owner. Test Alice/Bob/anonymous access, identifier substitution, list/pagination leaks, logout/revocation, and deletion. An unguessable ID and database row-level security are defense in depth, not replacements for endpoint authorization [CITED: https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html; https://www.postgresql.org/docs/current/ddl-rowsecurity.html].
- Use a maintained server-side session design with secure cookie attributes, CSRF defenses for state-changing requests, origin policy, expiry/revocation, and session rotation. OAuth security decisions should follow current OAuth security BCP, not ad hoc token handling [CITED: https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html; https://datatracker.ietf.org/doc/html/rfc9700].
- Enable persistent history only after owner-isolation tests pass and retention, export, deletion, backups, shared-device controls, and user-facing behavior are defined. The plan’s Alice/Bob checks are appropriate release gates [VERIFIED: `krishi_mitra_complete_improvement_plan.md:104-142`].

### 4. Consent, vendor data flow, and India DPDP research limits

- The inspected code path sends recorded audio to Sarvam transcription, uses the transcript plus supplied chat context in the text response flow, and sends response text to Sarvam TTS when enabled [VERIFIED: `backend/web_server.py:708-876`; exact provider model identifiers are quoted in Current Codebase Implications]. Make a concise Kannada/English just-in-time voice notice before recording, offer typed chat, and distinguish microphone permission from product consent. The notice must describe observed configuration and actual contracts, not promise that third-party copies are deleted or not retained [VERIFIED: improvement plan `krishi_mitra_complete_improvement_plan.md:144-178`; CITED: Sarvam policy scope at https://www.sarvam.ai/privacy-policy].
- Sarvam’s public privacy-policy page says it does not apply to content processed on behalf of enterprise customers and points to customer agreements for that processing. Therefore that website policy alone does not establish how Krishi Mitra’s API account handles audio/transcripts, retention, training, subprocessors, location, deletion, or transfers [CITED: https://www.sarvam.ai/privacy-policy]. No authoritative Groq API retention/data-processing statement was verified in this research; verify account-specific terms and agreements for both providers before approving the notice [ASSUMED].
- MeitY and India Code official pages could not be retrieved in this session (HTTP 403). Consequently this research does not assert which DPDP Act/Rules provisions are in force, commencement dates, exemptions, or that any proposed consent UX satisfies law. Have India privacy counsel verify the Act, Rules, commencement/amendment notifications, applicability, vendor roles/agreements, children’s data, notices, rights/grievance duties, retention, and breach process using current primary materials before launch [ASSUMED; official lookup URLs in Sources].
- Maintain a data-flow inventory for audio, transcript, prompt/history, profile, logs, backups, and every processor. Minimize data, avoid retaining raw audio by default, redact sensitive content from telemetry, and align actual retention/deletion operations with the notice. This is a risk-control recommendation, not a compliance conclusion [CITED: NIST Privacy Framework; improvement plan §4].

### 5. Deployment and a meaningful “1,000 users” test — later

- Preserve the local HTTP server as a development/demo path. Add production serving as an additive migration: HTTPS termination, stateless application instances, managed secrets, health/readiness and graceful shutdown, explicit timeouts/rate controls, separate staging/production configuration, and a managed relational store only when authenticated persistence is introduced. Use a production ASGI/API server after selecting and verifying the framework against the current app; do not infer production readiness from a threaded local server or from worker count [VERIFIED: `backend/web_server.py:9,1010`; CITED: https://fastapi.tiangolo.com/deployment/concepts/; https://fastapi.tiangolo.com/deployment/server-workers/].
- Define whether “1,000 users” means registered accounts, daily active users, or peak concurrent text/voice requests. Derive a workload model from realistic arrival rates, session think time, text/voice ratio, burst patterns, provider quotas, and expected external calls. Run smoke → normal-load → stress/spike → soak/breakpoint tests against staging and actual dependencies; inject provider latency/failure, throttling, and database saturation. Record stage and end-to-end p50/p95/p99, errors/timeouts, CPU/memory, queue/pool pressure, provider quota behavior, and cost. Set pass/fail SLO thresholds before the run and publish tested hardware, workload, limits, and fallbacks [CITED: https://grafana.com/docs/k6/latest/testing-guides/test-types/; https://grafana.com/docs/k6/latest/using-k6/thresholds/]. No 1,000-concurrent-user statement until the measured workload demonstrates it.

### 6. Kannada offline ASR/TTS feasibility — later research spike

- Offline ASR is technically plausible: AI4Bharat’s IndicConformer Kannada model card identifies Kannada and a 16 kHz mono input; it also documents a 120M-parameter conformer model and NeMo-based inference. This proves an available research/model path, not target-device speed, dialect/noise accuracy, license suitability, or production fitness [CITED: https://huggingface.co/ai4bharat/indicconformer_stt_kn_hybrid_ctc_rnnt_large].
- Offline TTS is also plausible to prototype: AI4Bharat’s IndicF5 repository lists Kannada among supported languages and usage requires generated text plus reference audio and transcript. It does not establish acceptable latency, memory, voice quality for target users, safe voice-data handling, or licensing fit; review model/code licenses and test reference-audio implications before adoption [CITED: https://github.com/AI4Bharat/IndicF5].
- Keep cloud Sarvam as the current voice path until a target-device benchmark and human Kannada review validate an alternative. Test clean/noisy and dialectal speech separately; report word/character error and slot-critical error rates, latency, memory, model download size, device power, licenses, and behavior with no network. “Full offline” additionally requires offline answer/retrieval, not just local speech recognition and synthesis [CITED: AI4Bharat model sources; improvement plan §6].

### 7. Bounded orchestration, migration, and test gates

- Use a single explicit pipeline: consent/auth gate when applicable → input validation/language/intent → crop resolution/clarification → reviewed evidence retrieval when relevant → deterministic rule engine for scheme evaluation → response composition → citation/policy validation and abstention → optional user-requested TTS → consent-aware storage and redacted metrics. Do not add autonomous agents or give a model identity, database, or eligibility authority [VERIFIED: `krishi_mitra_complete_improvement_plan.md:233-249`; VERIFIED: AI-SPEC line 11].
- Make changes additive: preserve local launch behavior and existing response fields; introduce optional fields or explicitly version intentional contract changes. Keep the evaluator unchanged, and add tests proving its results/statuses remain invariant across NLU/RAG changes. Stage database migrations with backup/rollback and do not enable persistence until the identity gate passes [VERIFIED: `krishi_mitra_complete_improvement_plan.md:251-315`].
- Phase 2 gates: existing backend tests pass; new ambiguity/unknown-crop/unclear-reply/correction/topic-switch tests pass; no unrelated slot overwrite; CLI and local web routes still work; evaluator outputs are unchanged. Later gates: citation/support/abstention evaluation; Alice/Bob/anonymous ownership suite; consent and provider-flow review; migration/rollback and staging smoke test; then measured load and offline benchmark. The current tests establish mocked provider and extraction coverage, not live quality or production capacity [VERIFIED: `backend/test_web_server.py:22-100`; validation gates are recommendations].
- Apply OWASP ASVS as a security verification checklist when designing the authenticated/deployed application; use the relevant controls selected for the actual stack rather than claiming broad compliance from following a checklist [CITED: https://owasp.org/www-project-application-security-verification-standard/]. Applicable security work expands in later identity, persistence, and deployment stages; Phase 2 still needs input validation, safe model boundaries, and regressions for the deterministic eligibility boundary.

2. **Crop-language ground truth:** Who supplies and approves dialect/transliteration aliases and ambiguous examples? An LLM-generated alias list is not a reliable gold set; farmer/SMS/extension-worker examples need consent and curation [VERIFIED: improvement plan `:48-64,80-102`].
3. **Knowledge freshness and jurisdiction:** Who reviews crop facts, source validity, location/season scope, and replacement dates? Without an owner and stale-source policy, citations can be valid URLs but wrong for the farmer [VERIFIED: improvement plan `:66-79`].
4. **Provider disclosure:** Which specific API-account terms, retention controls, training settings, processing locations, and subprocessors apply to the Groq and Sarvam credentials used by the deployed service? The public sources reviewed here do not resolve this [ASSUMED].
5. **Legal/privacy decision:** Which DPDP obligations and dates apply to this deployment and its processor arrangements? This remains a counsel checkpoint; no compliance assertion is made [ASSUMED].
6. **Production decisions:** Hosting, identity provider, persistence, registered-vs-concurrent target, voice/text workload mix, SLOs, and target offline hardware are not fixed by this research [VERIFIED: improvement plan `:205-232`; no decision is made here].
7. **Security verification scope:** Select applicable OWASP ASVS 5.0 controls for the chosen identity, session, API, and storage stack before deployment; this research does not provide a complete ASVS audit [CITED: https://owasp.org/www-project-application-security-verification-standard/].
